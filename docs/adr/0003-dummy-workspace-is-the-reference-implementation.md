## Context

The monorepo's M0 roadmap ("Workspace Standardization & Reference Implementation") made
`workspaces/dummy` the canonical example: standard Makefile, `package.json` metadata,
three-layer tests (plugin unit, hosting-app wiring, container smoke), compose harness for
dynamic loading, README shape. Root `AGENTS.md` and `README.md` already say "use dummy as
the template". The conformance matrix in `docs/inventory/workspaces.md` shows the rest of
the repo following dummy unevenly, and `dummy/LIFECYCLE.md` itself cites Makefile targets
that do not exist (ghost #12).

Three facts shape the decision:

- Dummy is meant to **demonstrate many things over time**: it will accumulate examples
  that stress what a workspace can contain. A new workspace almost never needs all of
  them. Copying dummy wholesale would saddle every new workspace with examples to delete.
- `.claude/commands/create-workspace.md` today is a prose prompt that scaffolds with
  `create-app` and ignores dummy entirely, so the reference is not what new workspaces
  actually start from, and the result depends on how an agent reads the prose.
- Dummy is on Backstage 1.49.2 (`backstage.json`), while the DevPortal host declares
  1.52.0 (ADR-0004). A reference that lags the host cannot prove that plugins built like it
  load on the host.

On the hosting app specifically: it proves static wiring and gives a dev loop, but loading
on DevPortal is proven by the container harness, which needs no hosting app. The two theme
workspaces broke on the 3.x app-shell contract that a plain `create-app` host never
exercises; single backend modules already test through `startTestBackend`. Where packages
in one workspace collaborate, however, the hosting app is the only place the collaboration
runs for real: unit tests mock the other side and the container harness runs on
placeholder config.

A reference that is only "an example" cannot settle a disagreement. It needs to be
normative, current, and usable piecewise.

## Decision

1. **Normative.** `workspaces/dummy` is the reference for every plugin workspace in
   `devportal-plugins`. A standard in this repo that describes workspace shape, packaging,
   testing or documentation cites dummy as its concrete form. When a standard and dummy
   disagree, the discrepancy is a defect fixed in the same change.
2. **A catalogue of elements, not a template.** Dummy is organised as a set of
   self-contained, documented **elements**, each demonstrating one thing a workspace may
   contain. The pickable catalogue starts with two elements, a frontend plugin and a
   backend plugin, and grows through dedicated milestones. The current list lives in
   operations (`new-workspace.md`) and in the tools below, never in this ADR.
3. **Hosting app by default; a proving harness always.** The hosting app is not a pickable
   element. It is generated by default and is **mandatory** when the workspace publishes
   static packages for plain Backstage or RHDH apps, or when its packages collaborate (one
   depends on or extends another in the same workspace). Otherwise it may be dropped with
   the reason recorded in the workspace's `AGENTS.md`. Independently, every workspace that
   exports dynamic artifacts carries the container harness that loads them on the host
   image. The exact trigger and its check are in
   [standard 01](https://github.com/veecode-platform/devportal-plugins-parent/blob/47ab25b/docs/standards/01-workspace-layout.md) (retired 2026-09-22; superseded by ADR-0009 §5).
4. **Workspaces are assembled, not copied**, by two tools that present the catalogue as a
   checklist and cherry-pick the chosen elements from dummy, renamed and wired together:
   - `create-workspace` (work in progress) creates a new workspace: the hosting app
     (pre-checked) plus the elements the developer picks.
   - `change-workspace` (future work) adds picked elements to an existing workspace.
   The result of either conforms to the standards without manual cleanup.
5. **Both tools are real implementations.** Each is delivered as a command or skill backed
   by a generator that copies, renames and wires files deterministically. Prose that asks
   an agent to improvise the steps is not an implementation. Delivering them is roadmap
   work (M7 for `create-workspace`; `change-workspace` is a candidate milestone).
6. **Dummy tracks the host's Backstage line.** Dummy pins the Backstage release the
   DevPortal image ships, as declared by `backstage.json` on `main` of
   `veecode-platform/devportal-core` (ADR-0004), and is upgraded first whenever that value
   changes; other workspaces follow. The file reads `1.52.0` on 2026-09-10.
7. **Conventions land in dummy first.** A change to the workspace convention (new Makefile
   target, new harness, new agent-context file) lands in dummy before it is required
   elsewhere.
8. **Never published.** Dummy's packages stay `private: true`.
9. **Deviations are recorded.** A workspace may deviate from dummy only with the reason in
   its `AGENTS.md`; a cross-cutting deviation needs an ADR here.

## Consequences

- **Positive**: one place to look and to measure conformance against; new workspaces start
  small and correct; existing workspaces can adopt new elements the same way; dummy can
  grow examples without taxing anyone; the host contract is proven on the reference before
  anywhere else; nothing ships unproven, without forcing ceremony where it proves nothing.
- **Negative / trade-offs**: dummy needs maintenance discipline it has not had (its
  `LIFECYCLE.md` is stale); two generators are engineering deliverables, not docs; the
  weekday automated bump must be pinned to the host version (decided in ADR-0004) or it
  pushes dummy past the host line. Of the five workspaces without a hosting app,
  `marketplace` (collaborating packages, no `yarn start` today) becomes conformance debt
  for M3; `ai-resources`, `aws-s3-catalog`, `veecode-theme` and `vertigo-theme` are exempt
  from the hosting app but currently lack the container harness too, which is debt of the
  other kind.
- **Follow-ups**: M2 fixes dummy's own docs; M6 upgrades dummy to the host line and writes
  the upgrade procedure; M7 delivers `create-workspace`; a candidate milestone delivers
  `change-workspace`; M3 completes standard 01 around the rule above and schedules the
  hosting-app and harness catch-ups; M4's `new-workspace.md` holds the element checklist;
  further milestones add elements (candidates listed in the roadmap).

## Alternatives considered

- **Copy dummy wholesale as the workspace template** (first draft, 2026-09-09) — rejected
  by the owner on 2026-09-10: dummy will demonstrate many features, so a blunt copy means
  every new workspace starts with examples it must delete.
- **Hosting app mandatory in every workspace** (second revision, 2026-09-10) — rejected the
  same day: a plain host would have shown the themes working while the real host was
  broken, single modules already test through `startTestBackend`, and the marketplace
  context cannot be reproduced in a plain host. Ceremony without proof.
- **Hosting app merely recommended for collaborating packages** — rejected: recommended
  becomes skipped under deadline; a checkable trigger (intra-workspace dependency or
  extension) does not.
- **Prose command only (the current `create-workspace.md`)** — the output depends on the
  agent's reading of the prose and cannot be tested; a generator can.
- **Generator-only (a script as the source of truth)** — a generator encodes the convention
  once and cannot be read as documentation or run as tests; dummy can be both, and the
  generators draw from it.
- **Upstream `community-plugins` as the reference** — it does not cover VeeCode's dynamic
  export, Makefile, harness or agent-context conventions.
- **Let dummy float on latest Backstage** — proves nothing about the host; the host line is
  what plugins are loaded into (ADR-0004).
