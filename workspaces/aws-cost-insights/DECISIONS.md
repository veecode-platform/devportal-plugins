# Plugin Decision Records

Workspace-local design decisions for `aws-cost-insights`, numbered `PDR-001`, `PDR-002`, …
and cited outside this workspace as `aws-cost-insights PDR-NNN`. They are plugin decision
records, not ADRs: decisions with cross-workspace or lasting weight live in the planning
repository `veecode-platform/devportal-plugins-parent` as `plugins ADR-NNNN`.

## PDR-001: Vendor the AWS Cost Insights Packages Instead of Maintaining a Fork

**Date:** 2026-09-08
**Status:** Accepted

The AWS-authored packages this workspace ships are **vendored**: copied into
`plugins/` with their provenance recorded in a `NOTICE` beside each one, rather than
consumed from a maintained fork.

Three packages come from `awslabs/backstage-plugins-for-aws` by way of the retired VeeCode
fork `veecode-platform/backstage-plugins-for-aws` at commit `cf408c11`, Apache-2.0, original
copyright Amazon.com, Inc. or its affiliates:

- `plugins/cost-insights-backend` — `@aws/cost-insights-plugin-for-backstage-backend`
- `plugins/cost-insights-common` — `@aws/cost-insights-plugin-for-backstage-common`
- `plugins/aws-core-common` — `@aws/aws-core-plugin-for-backstage-common`

`plugins/aws-cost-insights` (`@veecode-platform/plugin-aws-cost-insights`) is in-house and
is not vendored.

The sibling `aws-s3-catalog` workspace faced the same question at the same time and answered
it the same way, but that is its own decision and its own record (`aws-s3-catalog PDR-001`).
The two are independent, not one decision spanning both: this workspace vendored packages it
goes on to modify, while that one vendored a wrapper it keeps unmodified.

**The VeeCode modifications carried in the vendored backend** are the four the `NOTICE`
files name: an RBAC permission gate (every `/v1/*` route requires
`cost-insights-aws.cost.read`), an org-wide route (`GET /v1/org/:intervals`), per-account
projects (`GET /v1/projects` and `GET /v1/project/:project/:intervals`, the project being a
twelve-digit account id) and an entity account-id filter on the entity route.

**Rationale:** the fork was retired. Keeping a fork alive means carrying an upstream remote,
a merge cadence and a second release surface for four packages, three of which we barely
touch. Vendoring puts the code where it is edited, keeps provenance in a file that travels
with the package, and leaves one release surface. The cost is that upstream fixes are a
manual re-vendor rather than a merge; that is the trade accepted here.

## PDR-002: Prove the Cutover by Byte-Parity, Then Remove the Scaffolding

**Date:** 2026-09-08, amended 2026-09-09
**Status:** Accepted (the pins described below are gone; see the amendment)

Republishing a vendored package changes who builds it. To make the cutover reviewable, the
republished artifacts were required to be **byte-identical to what production was already
running**, modulo the intended version bump, before anything else was allowed to change.

Holding that gate needed two temporary measures at the workspace root, neither touching a
vendored file:

1. **A pinned export toolchain.** `@backstage/cli`'s tsconfig sets `useDefineForClassFields`
   with an ES2022 target, and esbuild changed how it emits TypeScript constructor parameter
   properties in 0.27.5. The fork resolved 0.27.3 and this workspace resolved 0.27.7, which
   added four bare class-field declarations to the compiled service. Pinning esbuild 0.27.3,
   with `typescript ~5.9.0` and `@backstage/cli ^0.35.4` to match the fork, made the output
   byte-identical.
2. **A transplanted dependency closure.** `rhdh-cli` seeds the exported plugin's install
   from this workspace's `yarn.lock`, so the closure baked into the published image is
   whatever that lock resolves. The committed lock disagreed with production on
   `@aws-sdk/client-cost-explorer` and could not express the packages production ships at two
   versions at once, so both locks were regenerated from the fork's lock at `cf408c11`, the
   input that produced the running images.

The gate was verified against the production bundle, compared recursively at every
`node_modules` depth: 205 packages against 205, nothing extra on either side, all 9
multi-version packages reproduced, and a byte diff of a single line, the intended version
field.

**Amendment, 2026-09-09.** The scaffolding was removed as planned. `@backstage/cli` returned
to `^0.36.0`, `typescript` to `~5.8.0`, and the esbuild and `@backstage/plugin-catalog-node`
resolutions were dropped, because the esbuild 0.27.5 output change is deliberate semantics
rather than a defect. Both locks were then regenerated by a normal install, letting esbuild
coexist at several versions per consumer range. The `fast-xml-parser` resolution stays; it is
a fork-era pin with its own follow-up. Validation moved from byte-identity to a functional
harness, and the versions moved to the first post-cutover line.

**Rationale:** byte-parity is a strong, cheap proof that a change of build owner changed
nothing else, and it is worth real ugliness for exactly one release. It is a terrible
steady state, because it freezes a toolchain for reasons unrelated to the code and makes
every future bump look like a regression. Recording both halves is the point: the pins were
temporary by design, and the record says when they went and what replaced them.
