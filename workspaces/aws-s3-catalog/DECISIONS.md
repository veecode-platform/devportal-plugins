# Plugin Decision Records

Workspace-local design decisions for `aws-s3-catalog`, numbered `PDR-001`, `PDR-002`, … and
cited outside this workspace as `aws-s3-catalog PDR-NNN`. They are plugin decision records,
not ADRs: decisions with cross-workspace or lasting weight live in the planning repository
`veecode-platform/devportal-plugins-parent` as `plugins ADR-NNNN`.

## PDR-001: Vendor the S3 Catalog Module as a Zero-Delta Wrapper

**Date:** 2026-09-08
**Status:** Accepted

`plugins/aws-s3-catalog-module` (`@aws/aws-s3-catalog-module-for-backstage`) is **vendored**:
copied from `awslabs/backstage-plugins-for-aws` by way of the retired VeeCode fork
`veecode-platform/backstage-plugins-for-aws` at commit `cf408c11`, Apache-2.0, original
copyright Amazon.com, Inc. or its affiliates. `NOTICE` beside the package is the provenance
record and `src/index.ts` keeps the Amazon license header.

The copy is **zero-delta**. The blob hashes of `.eslintrc.js`, `.gitignore` and `src/index.ts`
match the fork's, and `package.json` differed only in its version line at the time of
vendoring. **This workspace carries no VeeCode modification of its own**, which is why its
`NOTICE` names none.

The package is a one-line wrapper: `src/index.ts` re-exports the default of
`@backstage/plugin-catalog-backend-module-aws`, and that dependency is pinned exactly at
`0.4.24` rather than to a range. The pin is the point of the wrapper. `export-dynamic` runs
with `--embed-package @backstage/plugin-catalog-backend-module-aws`, so the exported artifact
carries that exact upstream module inside it. There are no tests, by design.

**Rationale:** the fork was retired, so the wrapper had to live somewhere. Copying it
unmodified keeps the option of re-vendoring from upstream cheap, since any future diff is
genuinely upstream's rather than a mix of upstream and local edits. Keeping the embedded
dependency exact rather than ranged is what makes the dynamic artifact reproducible: the
whole reason the wrapper exists is to freeze which upstream module gets embedded.

## PDR-002: Prove the Cutover by Byte-Parity, Then Remove the Scaffolding

**Date:** 2026-09-08, amended 2026-09-09
**Status:** Accepted (the pins described below are gone; see the amendment)

Republishing a vendored package changes who builds it. Before anything else was allowed to
change, the republished artifact was required to be **byte-identical to what production was
already running**, modulo the intended version bump.

Holding that gate needed a pinned export toolchain and a transplanted dependency closure at
this workspace's root, neither touching the vendored file. `rhdh-cli` seeds the exported
plugin's install from this workspace's `yarn.lock`, so the closure baked into the published
image is whatever that lock resolves; the lock was therefore regenerated from the fork's lock
at `cf408c11`, the input that produced the running image.

The gate was verified against the production bundle, compared recursively at every
`node_modules` depth: 238 packages against 238, nothing extra on either side, all 25
multi-version packages reproduced, and a byte diff of a single line, the intended version
field.

**Amendment, 2026-09-09.** The scaffolding was removed as planned: `@backstage/cli` back to
`^0.36.0`, `typescript` to `~5.8.0`, the esbuild and `@backstage/plugin-catalog-node`
resolutions dropped, and the lock regenerated by a normal install. The `fast-xml-parser`
resolution at `5.7.3` stays; it is a fork-era pin with its own follow-up and is the only
resolution left in the workspace root. The version moved to the first post-cutover line, and
validation moved from byte-identity to a functional check.

**Rationale:** byte-parity is a strong, cheap proof that changing the build owner changed
nothing else, and it is worth real ugliness for exactly one release. It is a bad steady
state, because it freezes a toolchain for reasons unrelated to the code and makes every later
bump look like a regression. Both halves are recorded so the pins read as deliberate and
temporary rather than as unexplained freezes.
